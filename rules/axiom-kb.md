# AXIOM Knowledge Base Rules

> These rules govern how the AXIOM knowledge system is maintained.

## Documentation Hierarchy

1. **`docs/PRD.md`** — Source of truth for what to build and in what order
2. **`docs/ARCHITECTURE.md`** — Source of truth for system structure and dependencies
3. **`docs/DECISIONS.md`** — Source of truth for why things are the way they are
4. **`docs/CHANGELOG.md`** — Chronological record of all changes

## Rules

### R1: No undocumented architectural decisions
Every choice that affects system structure, data flow, or methodology must be logged as an ADR in `docs/DECISIONS.md`. If you make a decision during coding that changes the architecture, stop and write the ADR first.

### R2: PRD phases are the only roadmap
Do not start work on a phase until the previous phase's acceptance criteria are met. Do not create features that span multiple phases without explicit approval.

### R3: Benchmark table integrity
Never fill benchmark table values with prototype results. Only Qlib-pipeline outputs from committed code are valid. Each row must be reproducible from a single command.

### R4: Wiki pages are LLM-compiled
Wiki concept pages in `wiki/concepts/` are generated by the LLM Wiki Compiler skill. They may be edited manually, but edits will be overwritten on next compilation unless the source material in `raw/` is updated.

### R5: Point-in-time discipline is non-negotiable
Any data source added to AXIOM must document its PIT boundary. Any backtest that violates PIT is invalid regardless of performance. See ADR-005.

### R6: Factor validation before inclusion
No custom factor enters the model without passing IC ≥ 0.02 validation. See `wiki/concepts/factor-scoring.md`.

### R7: Keep the changelog current
Every session that modifies code or documentation must append an entry to `docs/CHANGELOG.md` before committing.
